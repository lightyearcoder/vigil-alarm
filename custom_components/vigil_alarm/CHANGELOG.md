# Changelog

## 0.6.10

- **Notify groups can no longer be chosen; a channel can have several notify services.** A notify group (or any notify entity) cannot send an alarm with a high priority, so the notification form offers only `notify` services again. Under *Notify services* you tick one or more, so several people get the same message from one channel. A service that fails does not stop the others; the event `notification_failed` now also says which service. Channels made earlier keep working, also one that holds a notify entity.
- **Error messages of Home Assistant's own cards are in your language, and without a user name.** A refusal such as *Edwin may not arm in mode custom* showed in English on a standard card (for example the tile with the arm buttons) even when Home Assistant was set to Dutch, because Home Assistant always makes the text of this kind of error in English, whatever the language. Vigil now makes the text itself, in the language Home Assistant is set to (*Settings, System, General*; English when Vigil has no text in that language), names the mode as the person knows it and leaves the name of the user out: *Modus Aangepast is door u niet toegestaan om in te schakelen.* The same for *Mode ... is not enabled* and for a partition a user may not use (*Partitie Garage mag door u niet worden gebruikt.*). The Vigil card and the touch panel show the refusal of a mode in the language of the panel, with the name of the mode that was pressed (new line in the error table of both; a panel needs the new firmware for it, `firmware_version` 0.6.10, as for the other changes of this release). The words *Validation error:* that Home Assistant puts in front of such a message are gone too: the refusal is no longer a `ServiceValidationError` (for that kind Home Assistant adds them) but a `HomeAssistantError` of Vigil, with the same translation key. The six languages were already in `translations/`. It is the language of the system, not of the person's profile: Home Assistant does not give Vigil that. The Vigil card and the touch panel keep using the language of the panel.
- **Every tab of the admin panel has an address of its own** (`/vigil_alarm/overview` is `/vigil_alarm`, the others for example `/vigil_alarm/sensor`, `/vigil_alarm/log`, `/vigil_alarm/settings`). The *back* and *forward* buttons of the browser now switch between the tabs you looked at, a tab can be bookmarked, and a link opens straight on that tab. The buttons in the panel that take you to a tab (on the *Overview*, in the readiness list) do the same, so *back* returns to where you came from. Nothing to change on your side. (Changed in the panel script; reload the browser.)
- **Always-on sensors are listed apart.** On the *Sensors* page of the Vigil card and of the touch panel the list of a partition showed the always-on sensors (smoke, gas, water, tamper, 24-hour) under every partition, as if they belonged to it. They no longer do: the list of a partition has its own sensors only, and *Always on* is a choice of its own next to the partitions: on the card one more button in the row at the top of the page, on the touch panel one more step of the partition button at the top of the page. The *Sensors* button still counts what is open in the partition and in the always-on sensors together. Vigil sends the new list as `sensors_always` in the profile of a panel that can switch partitions; a panel with one partition keeps its one list. Needs the new firmware on the panel (`firmware_version` 0.6.10); an older firmware shows the list of the partition without the always-on sensors and has no *Always on* step.
- **More partitions than fit in the row on the touch panel.** With more than four partitions the row of buttons shows three at a time with an arrow on each side (dim when there is nothing further); *All* stays where it is. A partition chosen somewhere else (the *Sensors* page, or the return to the default partition) brings its own page into view. Up to four partitions nothing changes.
- **The column *Mode* on the *Partitions* tab.** The table *What each mode watches* had no title above the first column; it now says *Mode* (six languages).
- **The *Disarm* button is as high as the mode buttons.** On a wide card (a tablet, 800x480) the green *Disarm* button filled the whole height next to the status card. It is now a wide button of the same height as *Home*, *Away* and so on (72 px), and the *Sensors* button follows right under it. The touch panel already had this.
- **Sensors on the card: the list opens after the code.** After pressing *Sensors* and entering the code you came back on the main page, and only a second press showed the list without a code. The card went back at once because the state with the unlock reached it a moment after the answer to the code; it now waits for that state (at most 5 seconds) and opens the list. The second press without a code is gone with it.
- **README and pictures are made again** from the current screens: the touch panel and the card (six languages) and the admin panel (overview, sensor groups, adding a sensor) with the new logo. The overview picture was in the README twice; now once.
- **Guides:** the touch panel section of the six user guides describes the wide *Disarm* button, and the user guides, the tablet guides and `esphome/README.md` describe *Always on* and the arrows.
- **The touch panel firmware has the arrows and *Always on*** (`firmware_version` 0.6.10). Flash it to get them; without flashing everything keeps working.
- **Tested:** the profile lists the always-on sensors apart for every partition choice (and not for a panel with one partition); the card was run in a test browser: the list per partition, *All* and *Always on* give the right sensors, the badge counts both, and going back forgets the choice; the simulator draws six partitions with arrows and the page *Always on*.

## 0.6.9

- **The admin panel is no longer empty after reloading the page.** After a reload of the browser the *Vigil Alarm* page was often blank until you went to another page and back. The cause: the panel script first fetched its six text files and only then defined the panel, while Home Assistant makes the panel as soon as the script has loaded; the panel it made was an empty shell and never got its data. The script now defines the panel at once and waits for the texts inside, and a panel that was made too early gets what Home Assistant set on it again. Found by making the same sequence in a test browser: the page stayed empty before the change and showed all tabs after it. The first load can be a moment slower on a slow connection; after that the texts come from the cache.
- **A new colour for the logo.** The Vigil logo now has the blue of the *Home* symbol as it looks on the touch panel (#6897E6, with a flat shading) instead of the darker blue it had. The shield stays white; the eye is a darker shade of the same blue. You see it in the sidebar and the *About* page of the admin panel, on the Vigil card, on the touch panel (top bar), in the README and on the documentation website, whose accent colour is now that blue too. `tools/make_logo.py` makes the icons and the logo of the firmware from the old icons, so the colour can be changed in one place.
- **The info page of the touch panel shows whether a panel key is set.** A new line *Panel key: set* / *not set* (in the six languages of the panel) shows whether the device file has a `panel_key`, so you can see on the panel itself that the key got into the firmware. The key itself is never shown. Needs the new firmware (`firmware_version` 0.6.9); an older firmware just does not show the line, and everything keeps working.
- **The key window keeps the *New key* button.** While a freshly made key is shown, *Remove key* is hidden and *New key* stays, but it needs a second press (*Replace now?*) so you do not replace the key you are copying by accident. A line in the six languages says that a new key replaces this one at once.
- **The *About* tab has three links:** the user guide on the documentation website (https://lightyearcoder.github.io/vigil-alarm/, in the language of the panel: for example `/nl/` for Dutch), the GitHub project and *Report a problem*. The links to the guides on GitHub, to the other languages, to the touch panel page and to the releases are gone from that tab. The guides (six languages) describe it.
- **The count tiles of the Overview are one row** (partitions, sensor groups, sensors, confirmation rules, users, notifications, sirens, panels) on a wide screen, and the partition tiles above them use the same columns, so every tile stays above its neighbour. On narrower screens they wrap in rows of four and then two, still lined up.
- **The pictures in the guides are made again** with the new logo (the touch panel, including its info page, and the Vigil card on a phone and a tablet, all in six languages). `tools/compose_sheets.py` puts the simulator pictures together exactly as before.
- **README brought up to date:** the text names what Vigil does today (panels and tablets, the panel key, codes and lockout, alarm memory, self-test and heartbeat, practice mode and walk test, backups), the blue *Open HACS repository* button at the top is gone (the one under *Installation* stays), there are new pictures of the touch panel and the card, the badges use the logo blue, and the README links to the documentation website on GitHub Pages. The guides (six languages) and `esphome/README.md` list the new panel-key line.
- **The touch panel firmware has the new logo and the key line** (`firmware_version` 0.6.9). The panel works as before; flash it only to see them.
- **Tested:** the logo of the firmware is the one made from `brand/icon.png` and the four icons are the same blue; the texts of the new line are checked in all six languages and the info page is checked to have the line; neither frontend script waits at the top level and early properties are set again (the browser test itself lives outside the repository for now; it is on the backlog with the other frontend tests).

## 0.6.6

- **Panel identity: a key for every ESPHome panel.** The `source` of a call is plain text, so a call that only *says* it comes from a registered panel (for example from another Home Assistant account) was accepted as that panel. Now you can give an ESPHome panel a **key**: the key button in *Panels* makes one, shows it once (Vigil keeps only a SHA-256 digest of it) and a new key replaces the old one at once. The panel sends the key with every call (`panel_key` in the device file, from `secrets.yaml`; firmware 0.6.6), and Vigil refuses and logs every call in the name of that panel without the right key (`panel_refused`, reason `key`), on all services that take a `source`. Events `panel_key_created` and `panel_key_removed` are in the log. The key does not protect against someone who can read your ESPHome configuration or has administrator rights; use the encryption of the ESPHome API too.
- **A panel without a key works exactly as before** (nothing changes on update, panels do not have to be flashed), and *Ready for use?* has a new advice per panel without a key. Tablets and phones are told apart by their Home Assistant user and have no key. Calls that name no panel (automations, scripts, the dashboard) are not touched.
- **New texts in six languages** (the key dialog, the *Key set* / *No key* badge, the advice, the error), the guides in all six languages explain the key, and `esphome/README.md` has the step.
- **Tested:** 8 new tests for the key (shown once, only a digest kept, every service checked, other callers untouched, new key replaces the old, editing keeps it, tablets have none) and a firmware check that every call carries `key`.

## 0.6.0

- **Users and panels: the *Partitions* choice now sits just above the modes**, and the modes you can tick (*May operate in modes*, *May arm in modes*) are those of the partitions chosen (none chosen: those of all partitions). Un-ticking a partition removes the modes only that partition had.
- **Partitions: more than one alarm in one house.** A partition is a part of the house with its own state, modes and delays, for example the house and the garage. Add one under *Partitions* in the panel. The part you already have is the first partition (named under *Settings*; nothing is migrated). Every intrusion sensor is in exactly one partition (a new field *Partition* on the sensor); fire, gas, water, tamper and 24-hour sensors have none: they watch in every partition, and an alarm from them is **one alarm for the whole house**, ended by disarming it in any partition that is in it.
- **A new partition starts like the house:** the modes ticked and the exit delays, entry delay and alarm duration filled in are those of the first partition (before, *Night* was always ticked and the delays were empty).
- **Settings only has what applies to the whole system.** The name, modes, exit and entry delays, alarm duration and chime device of the first partition are no longer under *Settings*: they are the first row under *Partitions* (the chime device of the first partition is the default for partitions that have none). The card *What each mode watches* moved from *Settings* to the *Partitions* tab.
- **Find sensors has a *Partition* choice** (with more than one partition): the intrusion sensors you add go into that partition, with the suggested groups of that partition. Also fixed: the word *null* above the list in that dialog.
- **What each mode watches** (on *Partitions* and the *Overview*) has one card per partition, titled with the partition, and shows only the groups of that partition; the fire, gas, water, tamper and 24-hour sensors are in a card *Always on* below them.
- **Layout:** on the *Overview* the *Alarm* card is on its own on the full width above the counts; the tables on *Partitions*, *Sensor groups*, *Sensors* and *Confirmation rules*, and the cards of what each mode watches, keep equal column widths so the columns line up from one partition to the next.
- **Tab order from coarse to fine:** *Partitions*, *Sensor groups*, *Sensors*. With more than one partition the *Sensors* tab, like *Sensor groups*, has a table per partition; the fire, gas, water, tamper and 24-hour sensors are in a last table *Always on*.
- **The *Partitions* tab always lists every partition, the first one too** (it used to be hidden). You can rename it there and change its modes and times; *Partitions* is now the first tab after *Overview*, followed by *Sensors*. The first partition has no delete or copy button.
- **Sensor groups belong to one partition.** A sensor group has a partition (the first one for the groups you already have; config key `partition` on a sensor group, stored as nothing for the first). With more than one partition the *Sensor groups* tab has a table per partition, a group offers only the modes of its partition, and a sensor can only use groups of its own partition: saving a sensor with a group of another partition, moving a group away from sensors that use it, or deleting a partition that still has groups is refused with a message. A new partition has no groups yet: its table offers *Create default groups* (named like *Perimeter (Garage)*), and *Find sensors* does the same for the chosen partition.
- **Confirmation rules are listed per partition too** (the partition of their sensors; a rule still needs all its sensors in one partition), and the form only offers sensors of the same partition once you have picked one.
- **The log has a *Partition* column** (also in the CSV and JSON Lines downloads, as `partition`; it is filled in with one partition too). Events about a fire, gas, water, tamper or 24-hour sensor have none: they are for the whole house. The partition name is no longer in the `detail` of the entry.
- **One alarm entity per partition**, and, with more than one partition, an extra entity *All* whose state is the highest state of any partition (it reads `mixed` in the attribute `status` when they differ). Arming *All* arms every partition or none (all-or-nothing); a mode that a partition does not have is refused. The services `vigil_alarm.arm` and `vigil_alarm.disarm` take a new field `partition` (an id, or `all`). The existing entity keeps its entity id and unique id. New attributes `partition`, `partition_name` and `open_now_count`; with one partition nothing looks different.
- **Per partition:** modes and delays (under *Partitions*), who may arm and disarm (users and panels get a *Partitions* limit), sirens and notification channels (a *Partitions* filter; a channel without one serves all), chime and the readiness checks (*partition without sensors*, *partition nobody watches*). Confirmation rules must keep all their sensors in one partition.
- **Vigil card:** chips for the partitions and *All*, mode buttons from the modes of the selected partition, *Mixed* when partitions differ. The admin panel shows every partition on the *Overview*, a partition column in the tables and a coverage card per partition.
- **Partition choice is required everywhere and works the same way.** Users, panels, sirens and notification channels always have a *Partitions* choice: tick partitions or *All partitions* (an existing item with an empty list shows *All partitions* ticked). Safety alarms still sound on every siren.
- **Default partition per panel.** A panel has a required *Default partition* (one of its partitions, or *All*). A panel that may operate several partitions can switch between them and operate *All*; after the time set under *Settings → Panel screen → Return to default partition* (default 30 seconds, 0 = never) without touch it jumps back. New service `vigil_alarm.select_partition` (panel, partition).
- **Panel and tablet card always show what they operate:** the partition name or *All*, also when only one partition is allowed, and the brand *Vigil Alarm* with the logo in the top bar. The profile sensor has new attributes (`default_partition`, `view_*`, `partition_list`) that the firmware reads; the panel no longer needs `alarm_entity` in its YAML.
- **Tamper contact in the partition of its sensor.** The tamper input of a sensor now watches in the partition of that sensor, not in all: a panel (and the log) only shows the tamper of the partitions it operates, and a tamper alarm is an alarm of that partition. Fire, gas, water and 24-hour sensors still watch in every partition. A tamper sensor you add yourself (class *tamper*) has a *Partition* choice too (default *All partitions*). While the *Sensors* page is open the panel does not jump back to its default partition.
- **Touch panel:** the *Sensors* page has a button at the top with the partition whose sensors are listed; a tap goes to the next partition and *All* (the same choice as on the main page). The ring with the icon is 90% of its size, with the bottom in the same place.
- **Overview of the admin panel:** the Vigil logo and name stand above the alarm status and, with more than one partition, a coloured tile per partition (green off, blue armed, amber counting down, red alarm; no coloured bar, smaller text) in the same grid as the count cards below, so they line up; the line *All together* is gone.
- **What each mode watches** now has separate columns for the sensor groups and the sensors, one row per group.
- **User guides in German, French, Italian and Spanish** (`docs/user-guide.de.md`, `.fr.md`, `.it.md`, `.es.md`), translated by Claude; the English and Dutch guides and the tablet guides are updated for partitions.
- **Touch panel:** new firmware 0.6.0 with the partition row, the top bar and the logo; flash the panels to get it. A panel with firmware 0.5.6 keeps working and operates its default partition. Minimum ESPHome version 2026.9.
- Restart: the state of every partition is saved; an installation from before 0.6.0 loads as a single partition. Backups, the log and the notifications (a `[Partition]` suffix with more than one) know the partition.
- Tests: partitions in the core (`split_config`, `aggregate`) and in Home Assistant (entities, all-or-nothing, rights, one fire alarm for the house, sirens, channels, restart and the old state format).

## 0.5.4

## 0.5.3

- **Alarm memory with the path.** From the start of an entry delay until the alarm is disarmed, Vigil writes down **every sensor that opens**, with time and room (the Home Assistant area), including sensors that do not count in the armed mode and bypassed ones. The *Overview* tab has a card **Last alarm** with the steps in order and for each whether it counted; the log has `alarm_sensor_seen` for the ones that did not (those that counted are `sensor_faulted` as before). The Vigil card shows *Last alarm: 14:03 Front door → Hall → Living room* and the alarm entity has the attribute `last_alarm`. The memory survives a restart and stays until it is cleared (no code needed: the Overview card in the panel, the service `vigil_alarm.clear_alarm_memory` or an automation) or the next alarm replaces it. The touch panel does not show it yet.
- **Cancel window for false alarms.** A valid code within 60 seconds after the siren goes off (setting *Cancel window*, 0 = off) marks the alarm as a false alarm: the siren stops, the memory says *cancelled* and a message goes to the alarm channels. New event `alarm_cancelled`. Intrusion alarms only.
- **Duress code.** A second code per user (*Duress code*) that disarms like the normal one, with nothing to see anywhere and a quiet siren, while the channels with the new kind of message **Duress** get a silent message. Vigil refuses a duress code when no such channel exists, and when it equals another code. The event `duress_used` is only in the log and goes to those channels, never to the event entity or the last event. A duress disarm never counts as a cancelled alarm.
- **Chime.** *Chime* on a sensor: when it opens with the alarm off, a short sound through a siren, switch, light, button or script chosen under *Settings → Chime*. No alarm, no message, no log line. The event `chime` is on the event entity for your own automations.
- New events: `alarm_cancelled`, `duress_used`, `alarm_sensor_seen`, `alarm_memory_cleared`, `chime`. New settings: `abort_seconds`, `chime_entity`, `chime_seconds`.

## 0.4.0

- **Panel register (tab *Panels*):** register a panel or tablet with a panel id (the name of the ESPHome device). Per panel: the modes it may arm in, whether it may disarm, bypass, silence or acknowledge, its language, whether and when it may show the sensor list (*always*, *only after unlocking*, *never*), how long it stays unlocked, an optional installer code of its own, and *blocked*. Vigil enforces this on the server: a call from a registered panel that its profile does not allow is refused and logged (`panel_refused`), and bypassing from a registered panel always needs a user code. Calls from sources that are not registered are not restricted.
- **Profile entity:** every registered panel gets `sensor.<panel id>_profile` with what it may do and show. Sensor names are only in it while the panel is unlocked (or set to *always*); those attributes, and the sensor-name attributes of the alarm entity, are kept out of the recorder history. It holds no code, hash or key.
- **Unlock and Clear lock:** two buttons per panel, only in the Vigil panel (administrators), not as Home Assistant actions, logged with the administrator (`panel_unlocked`, `panel_lock_cleared`). A panel can also be unlocked with its installer code through the new action `vigil_alarm.unlock_panel`; that never disarms the alarm.
- **One lockout timer per registered panel**, plus one shared by everything else, and a separate timer for each panel's installer code.
- **Panel out of reach:** after 10 minutes without a connection to the ESPHome device you get a Repair and a message on the fault channels (`panel_offline`, `panel_online`). The alarm state is never changed by it.
- **Tablet as a panel:** a panel in the register can be bound to a Home Assistant user (a tablet with Home Assistant's own alarm card). Vigil enforces the profile on the user behind the call, which Home Assistant fills in and which cannot be imitated with a `source` text; the tablet gets its own lockout timer whatever name it sends, is never an administrator for Vigil, and bypassing from it always needs a code. An administrator may be chosen too (see below). A [tablet guide](docs/tablet.md) explains the set-up and the limits (Home Assistant has no permissions per entity).
- **Vigil card for a dashboard:** `type: custom:vigil-card`, loaded by Vigil for every user (no resource to add). It asks Vigil which panel belongs to the logged-in user (a new command, open to non-administrators, `vigil_alarm/tablet`) and then follows that panel's profile: state and countdown, only the modes the panel may arm in, *Disarm*, a keypad that opens only when you press a button (never by itself, so during an entry delay or alarm you first see what is going on), bypass if allowed, and the sensor list after a user code or the installer code (until then only *how many* sensors are open). It only reads and calls the normal actions; Vigil still enforces the profile on the server. Dutch and English, following the panel's language.
- **Tablet offline:** the card says hello every minute. A tablet whose card has been silent for 10 minutes gives the same Repair and fault message as an ESPHome panel (`panel_offline`, `panel_online`); the panel list shows *Vigil card active*. Only tablets that have used the card are watched, and Vigil remembers that over a restart.
- **Phones and tablets are one thing with ESPHome panels:** an entry in the register can be bound to a Home Assistant account (a tablet on the wall or a housemate's phone) and follows the entry's own settings: modes, disarm, bypass, silence and the sensor list with the installer code. **Any valid user code works** on such a device and the history shows whose it was; each entry has its own lockout timer.
- **Only registered accounts may operate:** as soon as one account is registered, every other ordinary Home Assistant account is refused before its code is looked at (`user_refused`, never counted towards a lockout). Administrators, automations, scripts and ESPHome panels are untouched, and an installation without a registered account does not change at all.
- **Advice in the guides:** give an administrator a second, ordinary account for daily use, lock the kiosk browser, and turn on *Code required to arm* to keep a passer-by from arming.
- **ESPHome firmware reads the profile:** a new folder structure (`esphome/vigil_alarm/` holds the firmware and the hardware file `guition-4848.yaml`, the folder above it only your device file). The panel takes everything it may do from its profile (modes, disarm, bypass, language, sensor list, unlock time) and uses the ESPHome device name as panel id and `source`; the substitutions `source`, `language`, `allow_bypass`, `sensor_list` and `sensor_unlock` are gone. A panel that is not registered shows *Not linked*, a blocked panel *Blocked*. The settings page with the language buttons is replaced by an info page (IP address, signal, uptime, firmware, panel id) behind the panel's installer code; the same code opens the sensor list, and bypassing always asks a user code. While locked, the panel shows only how many sensors are open. The firmware reports *Hardware ID*, *Capabilities*, *Firmware version* and *Profile version*, and screen sizes are set in one place (the hardware file).; please test and report.
- **Adding a panel is split by kind of device:** a first choice, *ESPHome panel* or *Tablet or phone running Home Assistant*, shows only the questions that fit. A tablet or phone asks for the Home Assistant account only (its panel id is made from the name). The language of a new panel starts as the language of the person who adds it; the choice *Home Assistant language* is gone.
- **No more *expected hardware* field:** the hardware the firmware reports is still shown on the panel card, but nothing needs to be filled in and there is no hardware advice any more.
- **ESPHome example:** updates over Wi-Fi now use `encryption` under `ota` (the key of the `api`) instead of an OTA password, as ESPHome advises; it saves memory and needs one secret less. The warnings about GPIO19 and GPIO20 are explained in the ESPHome README: the board wires them, they cannot be avoided.
- **The touch that wakes the screen is not a press:** while the screen is dark a see-through layer lies over the panel, so the first touch only switches the light on and does not also press the button under your finger. The layer goes when you lift the finger. A hardware file that calls `wake` on touch keeps working.
- **An administrator account may be chosen for a tablet or phone** (shown as *(admin)* in the list). That is the administrator's own responsibility, and the guides say so: the settings of the panel apply to everything that account does, on every device it is logged in on. On the panel Vigil gives it no administrator rights (a code is always needed to disarm and bypass, and tamper bypass needs a user with that right).
- **New scripts are not cached by the browser:** the address of the panel and the card now contains a fingerprint of the files, so a changed version is loaded without a hard refresh.
- **Countdown of the exit and entry delay is right on the panel and the card:** with 60 seconds it starts at 60 and the alarm is on at 0. Before, the panel counted against its own clock, which could be a few seconds off. Vigil now sends the seconds left (attribute `delay_left` on the alarm entity) and the panel and card count down from there.
- **Main page while disarmed shows only how many sensors are open** (panel and card), also after the sensor list was unlocked. The names are on the sensor list.
- **No false "sensor lost" messages after a restart of Home Assistant (Settings, card *Start-up*):** after the first 10 seconds Vigil already follows the sensors that are there, but a sensor that is still "unavailable" (MQTT or Zigbee that is still starting) is left alone: not reported as lost and not an alarm. As soon as all sensors are there, or after the wait (default 120 seconds, 10 to 900), Vigil reports the ones that are really gone. The event `startup_settled` in the log says how long it waited and which sensors were still missing. Reloading Vigil while Home Assistant runs does not wait. Only sensors are covered: other start-up reports (a panel that is out of reach, a failing heartbeat) keep their own timing.
- **Lock messages (follow-up):** the wrong code that starts a lock now says so at once ("Too many wrong codes. Try again in 5 min"), instead of "Invalid code" and a lock that only shows at the next try. The same message names the minutes still to wait (rounded up), and a permanent lock says an administrator must unlock it. The panel and the card show Vigil's refusals (invalid code, locked, no right to bypass, blocked, ...) in the language of the panel, whatever language Home Assistant answered in; before, an English text could appear on a Dutch panel.
- **Sensor list with a user code; bypass is a right:** the sensor list of a panel or the card now opens with the code of any Vigil user (or the installer code); the info page still needs the installer code. The action `vigil_alarm.unlock_panel` got an optional `scope` (`sensors` or `info`, default `info`, so older firmware keeps working). A wrong code for the list counts on the same timer as the other user codes of the panel. Users have a new right, *May bypass sensors*: without it a user can neither bypass nor restore a sensor, even with a right code (whoever may bypass may also restore; a tamper sensor needs *May bypass tamper* for both). Users saved before this existed keep the right until you untick it. The keypad says *Enter your user code* for the list.
- **Locking in steps (Settings, new card *Locking*):** seven settings. By default 3 wrong codes lock a panel for 5 minutes; after that 2 more wrong codes lock it for 15 minutes, then 2 more for 60 minutes, and 1 more wrong code locks it for good. A permanent lock only goes away with *Clear lock* at the panel (the button already existed) and the panel shows *Locked for good*. A right code sets the count and the step back to zero, and *Clear lock* does as well. The step, the count and a permanent lock are kept over a restart. The new event `code_locked_permanent` is also sent to the fault channels. The shared timer for everything that is not a registered panel never locks for good (nobody could lift it) and repeats the last wait. The old rule (5 wrong codes within 5 minutes) is gone; the count no longer expires by time.
- **Screen settings for the panels (Settings, new card *Panel screen*):** *Screen off after* (seconds without touch, 5 to 3600, default 30) and *Also let the screen go dark during an alarm* (default off: the screen stays on while the alarm is going off, so ALARM and its cause stay visible). The panel reads both from its profile entity (`screen_off_seconds`, `screen_off_on_alarm`). The screen only goes dark in a steady state (alarm off or fully armed), never while it counts down to arm or to enter. A half typed code, the list or the info that stays open too long first returns to the main page, and the screen goes dark after the same time again. The firmware substitution `backlight_timeout` is now `backlight_timeout_seconds` and only the start value until Vigil has told the panel.
- **No more jumping screen before it goes dark:** the panel used to return to the main page after 30 seconds and, during an entry delay or alarm, open the disarm keypad again at the very moment the light went out. It now does that after the screen is dark, so you see no jump and the keypad is simply there when you touch the screen. The setting `idle_timeout` is gone: the time is `backlight_timeout`.
- **Info page of the panel:** the back button now shows its arrow.
- **Keypad says which code:** under the code the panel and the card show *Enter your user code* or *Enter the installer code*. The code that unlocks the sensor list and the info page is now called the **installer code** (before: administrator code).
- **Sensor list in a useful order:** on the panels and the card the sensors that are most likely to be bypassed come first: open sensors that can be bypassed, then unreachable ones, then open fire and gas sensors (which cannot be bypassed), then bypassed ones, then the closed ones. Alphabetical within each group.
- **A panel always has a language:** the choice *Home Assistant language* is gone. A new panel starts with the language of the person who adds it (Dutch if that is Dutch, English otherwise). Panels made earlier with the old choice keep working.
- **Profile sensor with an old id is renamed:** a profile sensor made by an earlier build keeps the entity id it got then (Home Assistant never renames by itself), so the firmware could not find it. Vigil now renames it to `sensor.<panel id with underscores>_profile` at start-up, if that id is free. The *Not linked* screen of the panel also shows the sensor it looks for.
- **Changed:** the profile entity id is now `sensor.<panel id with underscores>_profile`, independent of the name you give the panel. The alarm entity no longer has the attributes `open_now_text`, `open_sensors_text`, `faults_text` and `panel_sensors` (they are in the profile of a panel, while allowed).
